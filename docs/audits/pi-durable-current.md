### PA-1 — P1 — Initial native creation has an unrecoverable publication window

**Proved defect.** Sources: [durable-runtime.ts:219](/Users/sk3_neels/Desktop/Sept/src/pi-integration/durable-runtime.ts:219), [durable-preflight.ts:129](/Users/sk3_neels/Desktop/Sept/src/pi-integration/durable-preflight.ts:129).

A real installed-worker SIGKILL immediately after that locator's directory fsync leaves an accepted run `active/ready`, invocation 0, valid database and `2.durable.json`, without the engine marker. Restart exits **1 before listening**, reporting missing engine evidence; provider calls remain **0** and the run snapshot is unchanged. Because root preflight visits every run, this legitimate interrupted initialization prevents the whole root from starting. The same mismatch exists between initial database creation and marker publication.

Root cause: initialization exposes native artifacts in several commits, while preflight treats every database-without-marker as incompatible published history, including an unstarted run created by this exact build. The existing malformed/missing-marker tests cover published history, not this genuine first-open crash.

Smallest correction: make initial native evidence publication recoverable, with a narrowly validated initialization state or staged publication before normal adoption. Preserve strict rejection of missing **published** history, mixed engines and corrupt state. Exercise real crashes at the initial database/locator/marker seams; simply moving the marker ahead of the locator leaves the earlier database window.

### PA-2 — P1 — Rotation replay discards already-delivered operator identities

**Proved defect.** Source: [durable-invocation.ts:260](/Users/sk3_neels/Desktop/Sept/src/pi-integration/durable-invocation.ts:260); installed consumers are [invocation-loop.ts:88](/Users/sk3_neels/Desktop/Sept/src/runtime/invocation-loop.ts:88) and [transitions.ts:62](/Users/sk3_neels/Desktop/Sept/src/runtime/transitions.ts:62).

The `rotationRequired` recovery branch returns `deliveredMessageIds: []` even when the exact admitted IDs remain durable. I exercised waiting → accepted operator direction → predecessor applies direction → native handover settles, then SIGKILL after handover JSON fsync but before Markdown/event/state publication. The pre-crash handover contains the accepted message. Restart reuses the native answer but rewrites that same handover with `operatorMessages: []`; the successor receives the already-applied direction in its pending operator-input block, instead of preserving it as predecessor delivery evidence. Four provider calls settle successfully, so a completion-only check misses the defect.

Root cause: the recovery path bypasses `DurableSubmission`'s delivery result and substitutes an empty array. It correctly defers messages that arrived after admission, but also defers IDs the predecessor already received. This loses exact handover evidence and can cause already-applied operator work to be repeated. The probe proves redelivery and receipt loss; it does not claim an observed duplicate external mutation or live-model decision.

Smallest correction: validate the recovered admission against the current conversation/request and carry its already-delivered IDs into the recovered rotation result. Keep genuinely later arrivals pending for the successor. Add an installed crash regression with a nonempty admitted operator capture, checking the handover IDs/text and absence of that ID from the successor's **pending** input block. Existing rotation fault cases have an empty capture.

### PA-4 — P1 — Durable rotation intent misclassifies a replayed ordinary response

**Proved defect.** Sources: [durable-invocation.ts:128](/Users/sk3_neels/Desktop/Sept/src/pi-integration/durable-invocation.ts:128), [durable-invocation.ts:185](/Users/sk3_neels/Desktop/Sept/src/pi-integration/durable-invocation.ts:185) and its recovery branch at line 260. The installed pinned native ordering is `GenerationTask.afterResponse` before assistant/answer settlement, in `node_modules/@earendil-works/pi-durable/dist/harness/generation.js:336`.

A real installed-worker SIGKILL after `rollover.json`'s `rotationRequired: true` directory fsync interrupts the hook before native steering admission or assistant settlement. Restart queues the single steer but native recovery also replays the original generation from its saved request cutoff. That provider request contains **no rotation steer**, so the fixture correctly returns the same valid ordinary control JSON. `observe()` sees only the durable rotation latch and validates that response as a handover. The run becomes **failed/terminal**, reason `Invalid durable handover fields`, after two provider calls, with no durable handover or successor. The restarted worker itself exits 0. This is a valid native request replay after a legitimate crash, not malformed provider output.

Root cause: a fsynced SEPT rotation **intent** is treated as proof that every later native response has received the steer. Native request/response settlement and placement of queued input occur later, so that assumption does not survive this ordering.

Smallest correction: distinguish rotation intent from the native generation that actually received the steer, using native request/submission placement evidence. Validate a recovered unsteered predecessor response as ordinary control, then allow the one admitted steer to produce the handover. Add an installed crash at this latch-before-native-settlement seam with replies selected from the actual provider input rather than a call-number sequence.

## Native ownership, necessity and acceptance evidence

The new native seam is mostly necessary contract adaptation. `Harness` owns generation, tools, submissions, storage and replay; the old `AgentSession` factories/invocation/recovery implementation are removed from production, with no selector, converter or parallel engine. Coding-agent remains a dependency for ModelRuntime, resources and seven tool implementations. Native task/submission storage is authoritative; admission adds the original pre-submit prompt and SEPT checkpoint acknowledgement that native storage cannot atomically derive from SEPT's separate queue/events. The guard uses supported synchronous close because native hook throws are advisory. Read-only preflight is justified because native storage/Harness opening performs initialization/recovery writes. Tool adapters preserve Pi's image support, edit preparation, bounds, cancellation and unsafe replay marking; resource/extension loading supplies approved trusted brain code without a legacy compatibility shim. PA-3 is the concrete removable residue; line count alone is not evidence of duplication.
